  - **Operational gotcha hit while verifying this:** lffci.org sits behind Cloudflare, which edge-caches static assets (e.g. `assets/css/react-admin.css`) for 30 days keyed on the full URL including `?ver=`. A CSS-only deploy that doesn't bump `AGENT_BUILDER_VERSION` can look "not applied" in a real browser even though the file is correct on disk (hash-verified) and correct via `curl` with a cache-busting query param — Cloudflare is serving its own stale cached response for the *unchanged* `?ver=X.Y.Z` URL. No plugin-level Cloudflare integration exists on this site to purge it via WP-CLI; the practical fix is that the version bump step of the deploy workflow already solves this (new `?ver=` → cache miss) — but don't be fooled mid-session into thinking an asset-only fix didn't take when testing against an unbumped version. To force a real check before bumping, swap the stylesheet's `href` client-side (e.g. via the browser JS console) to a cache-busted URL rather than trusting a normal reload, even a hard one — the browser's own cache isn't the problem, Cloudflare's is.

## Deploy workflow

reproduce → root-cause → fix → lint → version bump → deploy to lffci.org → verify live → check `debug.log` → commit → push. See global memory `feedback_deploy_workflow.md` for the full mechanics (scp to `/tmp`, `sudo cp` into place, `chown www-data:www-data`, hash-compare local vs remote before committing).

Live plugin path on lffci.org: `/var/www/lffci.org/public/wp-content/plugins/agent-builder` (note: directory is `agent-builder`, **not** `agent-builder-wp`). WP-CLI: `ssh lffci "sudo -u www-data wp --path=/var/www/lffci.org/public <command>"`.

**React admin surfaces** (`src/*/index.js`) need `npm run build` (wp-scripts) before deploying — the built output in `build/` is git-tracked and must be committed alongside source changes, not just the source.

**Bundled agent `abilities.json` edits** need a re-sign after deploying, or the agent gets blocked outright: `\Agentic\Abilities_Manifest::save_integrity_hash('<slug>')` via `wp eval`. The check is an HMAC against a server-local `abilities-signature` file (not in git, not in any DB table) — a content change with no matching re-sign fails closed with "Manifest signature mismatch" (audit log: `integrity_failure`). Discovered the hard way in 3.3.70.

## Key architecture notes

- **Basic/Advanced UI mode**: `Admin_Menu_Handler::is_advanced_mode( string $screen = '' )`, backed by the `agentic_ui_mode` option (global) with optional per-screen user-meta overrides. Established pattern for REST-fed React views: include `'is_advanced' => $is_advanced` in the payload (see `tools_payload()`/`approvals_payload()`/`logs_payload()`/`skills_payload()` in `class-admin-pages-rest.php`), consume as `data.is_advanced` in the corresponding `XxxView` component. For classic-PHP admin pages, call `is_advanced_mode('screen-name')` directly and gate markup — but remember to keep any hidden-in-Basic form field as a `<input type="hidden">` fallback so its value still round-trips on submit rather than getting silently reset.
- **Skills vs Tools vs Abilities**: Skills (`Skills_Registry`, `library/skills/*/SKILL.md`) are reusable instruction bundles teaching *how* to sequence tool calls — loaded into agent context via progressive disclosure. Tools (`Tools_Registry`, `library/tools/*/tool.php`) are the actual callable functions. Abilities (`Abilities_Manifest`, `abilities.json` per agent) are the separate *security/risk-tier* boundary — skills' `allowed-tools` is advisory scoping only, never a second permission system. Risk is normally declared per tool-name (flat `"risk"` key), but since 3.3.71 a tool whose actions genuinely differ in risk (a `list`/`get` read vs. `create`/`update`/`delete` writes) can add a `"risk_by_action": {"list": "none"}`-style map alongside the flat `risk` — `Abilities_Manifest::get_effective_risk()` takes an optional `$call_action` and checks that map first. Only narrows which of the tool's *own* actions the flat risk applies to; still can't go below the tool's own intrinsic default (`wp_agentic_tools.risk_level` / `get_risk_level()`), so the "manifest can only escalate, never downgrade" invariant holds exactly as before.
- **Mirror commits**: this repo receives periodic "mirror" commits from a separate private upstream, authored by "Agent Builder Release <support@agentic-plugin.com>", messages like "Release free (WPorg) vX.Y.Z" / "Mirror from private agent-builder". These are not something to create manually, aren't suspicious, and shouldn't be reverted/reconciled against local work — they're an established part of the workflow. Check `git log` for a newer such commit than what's live on lffci.org at the start of a session.
- **i18n**: fully built out as of 3.3.46 (11 locales, PHP `.po`/`.mo` + per-handle JS JSON). If new webpack entries or translatable strings are added, the `.pot` needs regenerating with `wp i18n make-pot . languages/agent-builder.pot --slug=agent-builder --exclude=build` (must exclude `build/` or webpack output pollutes references), and JS translations need the `make-json` output manually renamed from per-source-file to per-*handle* `{domain}-{locale}-{handle}.json` — WordPress's `load_script_textdomain()` won't find the default hashed filenames.
