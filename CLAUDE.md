# Agent Builder (WordPress.org free tier)

`renduples/agent-builder-wp` — the free/WordPress.org-facing repo for **Agent Builder**, a multi-agent AI orchestration plugin for WordPress. Live test/dev deployment is **lffci.org** (Lets Farm Financial Cooperative, Inc.), reachable via `ssh lffci`.

- **3.3.73 — Media Library's "Ask AI" launcher was invisible on the screen almost everyone lands on.** Found via general Agent Orchestrator testing (asked "which wp admin screens have launchers," it correctly listed Media as enabled — user reported "I don't see it at media"). `includes/class-admin-surfaces.php`'s Media implementation was structurally different from the other four contextual-launcher screens from the start: Dashboard/Plugins/Users/Comments all get an always-visible toolbar-level launcher, but Media only had `attachment_fields_to_edit` (fires inside an individual image's edit modal — requires clicking into an item first) and `media_row_actions` (fires only in List View, a manually-toggled alternate mode WordPress doesn't default to — the default is Grid View). Neither is visible on first landing on Media Library. Two-part fix: (1) added `media_toolbar_launcher()` on `restrict_manage_posts` (scoped to `post_type === 'attachment'`, since that hook is shared across every post-type list table) to cover List View, matching the existing `restrict_manage_users` pattern for Users; (2) Grid View needed something entirely different, since it's rendered client-side by Backbone (`wp.media`) and no PHP action fires inside it at all — added `media_grid_launcher_js()` on `admin_footer-upload.php` that injects the identical launcher HTML via JS. First attempt (a one-time `querySelector`-and-append at script-parse time) silently lost a timing race against Backbone's own async render of that toolbar region, which clears and repopulates the container — the launcher would insert, then get wiped a moment later with no error. Fixed with a `MutationObserver` on `document.body` (not the toolbar node itself, since Backbone may replace that element outright rather than mutate it in place) that re-inserts on every DOM change, idempotent via an existing-launcher check. Verified live end-to-end: launcher visible immediately in default Grid View, click opens the chat overlay with WordPress Assistant and the correct pre-filled prompt, confirmed no leak onto Posts/Pages (`restrict_manage_posts` fires for every post type, so the `attachment`-only guard is required), `debug.log` clean.

Since it's the fresh-install *default*, and the last public WordPress.org release (v3.3.46) postdates that first commit by a wide margin, this almost certainly affects real installed sites, not just lffci.org. The bad slug had propagated to **two** separate storage locations that both needed fixing: the `agentic_editor_sidebar_settings` option itself, and a `wp_agentic_deployments` row (type `admin_ui`) that `Deployments_Migrator` had copied it into verbatim the first time it ran — the row is the one the classic Editor tab and the `manage_editor_sidebar_agent` tool actually read once any rows exist, so fixing only the option (my first pass) visibly changed nothing. Fixed both: the fresh-install default itself, a new idempotent one-time migration (`Activator::migrate_editor_sidebar_seo_slug()`, gated on its own flag option, wired into the existing `run_migrations()` — same place `migrate_agent_personas()`/`migrate_agent_overrides()` live) that corrects the option and either renames or drops-as-duplicate the bad Deployments row, and triggered it for existing installs the established way: bumping `AGENT_BUILDER_DB_VERSION` (2.13.1 → 2.13.2) so `Activator::maybe_upgrade()`'s cascade reaches it. - **3.3.71 — Agent Orchestrator's tools were unusable for read-only questions; new project-wide `risk_by_action` capability.** User report ("where are agents currently deployed?" — a purely informational question) surfaced two stacked bugs, both from live chat-driven testing:
  1. **Root cause**: all 8 Agent Orchestrator tools required in-chat confirmation for *every* call, including pure `list`/`get` lookups — risk was declared per-tool-name in `abilities.json`, and `Tool_Executor::execute()`'s risk gate (`Abilities_Manifest::get_effective_risk()`) never looked at which `action` was actually being called. Asking to see current deployments made the LLM call all 8 `manage_*` tools and get 8 separate approval prompts. Fixed by extending the risk system, not just this feature: `abilities.json` entries can now declare an optional `risk_by_action` map (e.g. `{"risk": "low", "risk_by_action": {"list": "none"}}`) that `get_declared_risk()`/`get_effective_risk()` consult when a `$call_action` is passed. Preserves the existing, documented invariant exactly — "agent manifests can only escalate risk, never downgrade it below the tool's own intrinsic default" — because the final result is still `max(tool_intrinsic_default, resolved_manifest_risk)`; this only works at all because all 8 tools' own registered intrinsic default in `wp_agentic_tools` was already `none` (confirmed via DB query before implementing), so `risk_by_action` narrowing the manifest side down to `none` for reads correctly resolves to `none` overall, while writes still floor at the tool's declared `low`/`medium`/`high`. `Tool_Executor::execute()` now passes `$arguments['action']` through to the risk gate. Available to any agent/tool going forward, not just Agent Orchestrator.
  2. **Compounding display bug**: when multiple tool calls in one turn each needed confirmation, the response text and the "Proposed Change" card described two *different* proposals (last-seen vs first-seen, from two loops in `class-agent-controller.php` that disagreed) — confusing even before bug 1 existed, and would recur for any future multi-write turn. Root cause: a code comment already said "stop looping as soon as a tool needs user sign-off," but the loop didn't actually `break` — it kept executing (and creating proposals for) every remaining tool call in the batch. Added the missing `break`.
  - Both verified live end-to-end post-fix: the same "where are agents currently deployed?" query now returns a complete, direct, correctly-worded answer with zero confirmation prompts.

The fix is *not* necessarily the deactivate/reactivate the error message suggests (disruptive — cycles every agent) — call `\Agentic\Abilities_Manifest::save_integrity_hash('<slug>')` via `wp eval` for just the one agent right after deploying its updated `abilities.json`. **Any future edit to any bundled agent's `abilities.json` needs this same re-sign step as part of the deploy, every time** — easy to forget since nothing in the deploy workflow currently calls it out, and the DB-only tables (`wp_agentic_agent_library` etc.) don't reflect it either.
- **3.3.69 — Truncated LLM responses were silently shown as complete.** User report: Editorial Director's answer to a tool-heavy multi-step request ("Find thin posts, then coordinate rewriting and SEO improvements") stopped mid-sentence right as it was about to write out a list, with no error and no indication anything was wrong. Root cause traced via the audit log (`chat_complete` details showed 8 tool iterations, response ending exactly at "Here's the list of your published posts:") to Gemini returning `finishReason: MAX_TOKENS` on the final completion — the model's own "thinking" tokens across an 8-iteration tool loop evidently ate the output budget before the visible answer was written. `includes/class-llm-client.php`'s **non-streaming** Google/Anthropic response parsers already correctly mapped this (`normalize_google_response()`'s `MAX_TOKENS → 'length'`, `normalize_anthropic_response()`'s `max_tokens → 'length'`), but the **streaming** parsers (`parse_google_stream_chunk()`, `parse_anthropic_stream_chunk()`) — the actual path the interactive Chat page uses — never read the provider's finish/stop reason at all, so streamed truncation was invisible even in principle. Fixed both streaming parsers to capture and map it identically to their non-streaming counterparts (careful not to override an already-detected `'tool_calls'` finish, since Gemini can report `STOP` on the same chunk that carries the functionCall). `includes/class-agent-controller.php`'s `chat()` (interactive) and `run_autonomous_task()` (scheduled tasks) now check for `finish_reason === 'length'` at the point they accept the model's final text and append a visible truncation notice rather than presenting the fragment as complete — confirmed via `WP_REST_Server`'s SSE `'end'` event, whose `response` field fully overwrites the streamed bubble content client-side (`assets/js/chat.js`), so the notice reaches the live chat UI immediately, not just on reload. **Scope note**: `includes/class-agent-job-processor.php` (the separate, narrower agent-creation-wizard background job, `agent_id: 'assistant-trainer'`) has the same class of gap — never reads `finish_reason` at all — but was left out of this pass as a distinct, lower-frequency flow; worth the same treatment later. **Verification gap**: the exact truncation from the original report could not be reliably reproduced live afterward (LLM output length is non-deterministic, two follow-up attempts — including one deliberately engineered to demand a very long answer — both completed without truncating) — the fix is verified at the code level (traced against the documented provider finish-reason semantics and the existing, already-correct non-streaming mapping) and deployed, but not confirmed by observing the actual warning render live.

### What just happened: Skills feature overhaul (3.3.57–3.3.61)

Skills (SKILL.md instruction bundles that teach agents workflows) had a complete data layer and admin UI since v2.5.2 but were **never actually wired into agent runtime** — `Skills_Registry::get_for_agent()` was dead code. This got fixed and substantially built out:

- **3.3.57** — Spec-aligned with [agentskills.io](https://agentskills.io) (the open standard Anthropic and Google's Android Skills both use): `allowed-tools` frontmatter, `license`/`compatibility`/`metadata` fields, spec validation. Wired skills into the actual prompt pipeline via progressive disclosure (name+description always in context; full body loaded on demand via a new `load_skill` tool — mirrors the existing OKF knowledge-wiki pattern). Bundled skills now auto-refresh from disk on plugin updates if never user-edited (`source_hash` tracking + a proper versioned schema migration — this surfaced and fixed a real pre-existing bug: `dbDelta()` can't parse `CREATE TABLE IF NOT EXISTS`, so this whole class of schema migration had likely been silently failing plugin-wide). Added 4 new bundled skills: `woocommerce-catalog-management`, `woocommerce-order-management`, `wp-content-authoring`, `gutenberg-blocks`.
- **3.3.58** — Skills now always shows in the admin menu (was hidden entirely in Basic mode); the Basic/Advanced split moved onto the page itself instead.
- **3.3.59** — Browse Community Skills now supports **3 sources** with a switcher: `github.com/WordPress/agent-skills` (official WordPress org repo, Basic mode default — this is the reputable, human-reviewed alternative to ClawHub's open-publish model), `github.com/anthropics/skills` (Advanced only), and OpenClaw/ClawHub (Advanced only, pre-existing). Fixed two real bugs found along the way: the import payload was `sanitize_text_field()`'d as a whole JSON blob before decoding (corrupts content with `<...>` in it — routine in WordPress examples), and cross-source dedup matched on slug alone (two registries' same-named skill could clobber each other).

## Deploy workflow

reproduce → root-cause → fix → lint → version bump → deploy to lffci.org → verify live → check `debug.log` → commit → push. See global memory `feedback_deploy_workflow.md` for the full mechanics (scp to `/tmp`, `sudo cp` into place, `chown www-data:www-data`, hash-compare local vs remote before committing).

Live plugin path on lffci.org: `/var/www/lffci.org/public/wp-content/plugins/agent-builder` (note: directory is `agent-builder`, **not** `agent-builder-wp`). WP-CLI: `ssh lffci "sudo -u www-data wp --path=/var/www/lffci.org/public <command>"`.

**React admin surfaces** (`src/*/index.js`) need `npm run build` (wp-scripts) before deploying — the built output in `build/` is git-tracked and must be committed alongside source changes, not just the source.

**Bundled agent `abilities.json` edits** need a re-sign after deploying, or the agent gets blocked outright: `\Agentic\Abilities_Manifest::save_integrity_hash('<slug>')` via `wp eval`. The check is an HMAC against a server-local `abilities-signature` file (not in git, not in any DB table) — a content change with no matching re-sign fails closed with "Manifest signature mismatch" (audit log: `integrity_failure`). Discovered the hard way in 3.3.70.

## Key architecture notes

- **Basic/Advanced UI mode**: `Admin_Menu_Handler::is_advanced_mode( string $screen = '' )`, backed by the `agentic_ui_mode` option (global) with optional per-screen user-meta overrides. Established pattern for REST-fed React views: include `'is_advanced' => $is_advanced` in the payload (see `tools_payload()`/`approvals_payload()`/`logs_payload()`/`skills_payload()` in `class-admin-pages-rest.php`), consume as `data.is_advanced` in the corresponding `XxxView` component. For classic-PHP admin pages, call `is_advanced_mode('screen-name')` directly and gate markup — but remember to keep any hidden-in-Basic form field as a `<input type="hidden">` fallback so its value still round-trips on submit rather than getting silently reset.
- **Skills vs Tools vs Abilities**: Skills (`Skills_Registry`, `library/skills/*/SKILL.md`) are reusable instruction bundles teaching *how* to sequence tool calls — loaded into agent context via progressive disclosure. Tools (`Tools_Registry`, `library/tools/*/tool.php`) are the actual callable functions. Abilities (`Abilities_Manifest`, `abilities.json` per agent) are the separate *security/risk-tier* boundary — skills' `allowed-tools` is advisory scoping only, never a second permission system. Risk is normally declared per tool-name (flat `"risk"` key), but since 3.3.71 a tool whose actions genuinely differ in risk (a `list`/`get` read vs. `create`/`update`/`delete` writes) can add a `"risk_by_action": {"list": "none"}`-style map alongside the flat `risk` — `Abilities_Manifest::get_effective_risk()` takes an optional `$call_action` and checks that map first. Only narrows which of the tool's *own* actions the flat risk applies to; still can't go below the tool's own intrinsic default (`wp_agentic_tools.risk_level` / `get_risk_level()`), so the "manifest can only escalate, never downgrade" invariant holds exactly as before.
- **Mirror commits**: this repo receives periodic "mirror" commits from a separate private upstream, authored by "Agent Builder Release <support@agentic-plugin.com>", messages like "Release free (WPorg) vX.Y.Z" / "Mirror from private agent-builder". These are not something to create manually, aren't suspicious, and shouldn't be reverted/reconciled against local work — they're an established part of the workflow. Check `git log` for a newer such commit than what's live on lffci.org at the start of a session.
- **i18n**: fully built out as of 3.3.46 (11 locales, PHP `.po`/`.mo` + per-handle JS JSON). If new webpack entries or translatable strings are added, the `.pot` needs regenerating with `wp i18n make-pot . languages/agent-builder.pot --slug=agent-builder --exclude=build` (must exclude `build/` or webpack output pollutes references), and JS translations need the `make-json` output manually renamed from per-source-file to per-*handle* `{domain}-{locale}-{handle}.json` — WordPress's `load_script_textdomain()` won't find the default hashed filenames.
