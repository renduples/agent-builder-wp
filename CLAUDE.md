# Agent Builder (WordPress.org free tier)

`renduples/agent-builder-wp` — the free/WordPress.org-facing repo for **Agent Builder**, a multi-agent AI orchestration plugin for WordPress. Live test/dev deployment is **lffci.org** (Lets Farm Financial Cooperative, Inc.), reachable via `ssh lffci`.

- **3.3.68 — Dashboard Quick Actions: user-picked actions were silently invisible.** User report: checked "Tools" in the Dashboard's "Manage Actions" picker, saved, and it never appeared as a button. Confirmed the save itself was correct (`agentic_quick_actions_enabled` user meta already had `tools` in it) — the bug was purely a client-side render filter in `src/dashboard-app/index.js` (`QuickActionsCard`): any catalog entry flagged `advanced: true` (Tools, Skills, Approvals, Publish, Settings) was filtered out of the rendered button rows unless `data.is_advanced` (`Admin_Menu_Handler::is_advanced_mode('dashboard')`) was also true — i.e. a personal, explicit per-user selection was being silently overridden by an unrelated global/screen Basic/Advanced setting, with no UI explanation why. Same root principle as 3.3.64 ("Basic/Advanced should only ever affect a page's own content, never navigation/what's reachable") — removed the `(!a.advanced || data.is_advanced)` condition from both the `primary` and `secondary` filters so `enabled` alone (the user's actual choice) is authoritative; the "Advanced" note next to those items in the picker itself stays as an informational label. Verified live on lffci.org: Tools now renders correctly in the Quick Actions row while the Dashboard is still in Basic mode.
- **3.3.67 — Publish gets a Basic/Advanced switch; new bundled agent, Agent Orchestrator.** Publish was the last screen missing the Basic/Advanced content split the other four screens got in 3.3.63. Advanced mode is the unchanged 8-tab classic UI (Admin bar, CLI, Editor, Event Listeners, Frontend Modal, Gutenberg Blocks, Scheduled Tasks, Shortcodes). Basic mode embeds a chat with a new bundled agent, **Agent Orchestrator** (`library/agents/agent-orchestrator/`), fully tool-backed for all 8 areas via 8 new tools in `library/tools/` (`manage_agent_shortcode`, `manage_frontend_modal_agent`, `manage_gutenberg_block_agent`, `manage_editor_sidebar_agent`, `manage_admin_bar_launcher`, `manage_scheduled_task`, `manage_event_listener`, `manage_cli_settings`) plus a new Skill (`library/skills/agent-deployment/SKILL.md`) documenting the workflow per channel. Scheduled-task and event-listener CRUD (the two with real side effects beyond a `Deployments` row write — WP-Cron scheduling, dual-write) were extracted out of `Admin_Ajax` into shared `Agent_Lifecycle` static methods so the classic AJAX handlers and the new tools call the same code, not duplicates. The chat embed reuses the existing dedicated Chat page's template (`templates/chat-interface.php` + `assets/js/chat.js`) via a new `$agentic_force_agent` var that suppresses the agent-switcher and hard-codes Agent Orchestrator — not the `[agentic_chat]` shortcode path. New sites get Agent Orchestrator active from first install as usual; existing sites get it via the standard `Activator::maybe_upgrade()` cascade, triggered by bumping `AGENT_BUILDER_DB_VERSION` (2.13.0 → 2.13.1) — no new migration code needed, this is the established, sanctioned mechanism for shipping anything that must auto-apply post-update without a manual re-activation.
  - **Two real bugs found and fixed during live chat-driven verification** (drove `manage_agent_shortcode` through actual chat on lffci.org rather than only checking each tool's PHP in isolation):
    1. `assets/js/chat.js`'s tool-approval flow has a generic convention (pre-dating this feature, used by `create_form`/`list_forms`/etc.): if an approved tool's result has a top-level `shortcode` key, it's rendered verbatim in backticks as "paste this shortcode" copy — the convention expects a plain string. `manage_agent_shortcode`'s `do_create()`/`do_update()` returned a *nested object* under that same key name, so the chat literally rendered `[object Object]` instead of the shortcode. Fixed by renaming the nested summary to `deployment` and adding a plain-string `shortcode` key alongside it, matching the existing convention instead of colliding with it.
    2. Far more serious: `Deployments::save()` (`includes/class-deployments.php`) rebuilds every DB column from only the keys present in the `$data` array passed to it (via `prepare_row()`) — it was never a true partial update. Any caller that passes a subset of fields on an *update* (both the classic Edit form for shortcodes and every one of the new tools do this — none of them re-send `type`, `page_id`, or `created_at`) silently blanks the omitted columns: `type` gets reset to `''` (which drops the row out of every classic tab's listing, since those filter `WHERE type = ...`), and `created_at` gets overwritten to "now" on every single edit. Caught by renaming a test shortcode via chat and finding the classic Shortcodes tab still showed the old label — traced through the audit log, then confirmed directly via `wp eval` calls to `Deployments::save()` bypassing the LLM entirely. Fixed in `save()`: on update, fetch the existing row and `array_merge()` it under the incoming `$data` *before* calling `prepare_row()`, so omitted fields survive. This bug predates this session's new tools — the classic Shortcodes tab's own Edit button has always had the same partial-update pattern and would have hit it too; nobody had apparently exercised Edit enough to notice `type` silently going blank.
  - **Verification gap**: only 2 of the 8 tool-backed areas (`manage_agent_shortcode`'s create/update, `manage_frontend_modal_agent`'s enable/re-enable) were actually round-tripped through chat and cross-checked against the classic tab; the browser extension used for testing repeatedly dropped its tab-group connection mid-session (lost the logged-in WordPress session twice, required manual re-login), so the remaining 6 tools (`manage_gutenberg_block_agent`, `manage_editor_sidebar_agent`, `manage_admin_bar_launcher`, `manage_scheduled_task`, `manage_event_listener`, `manage_cli_settings`) were only exercised by reading their PHP, not by driving them live. Given the `Deployments::save()` fix is shared infrastructure (not per-tool), and the two verified tools both hit it correctly post-fix, the remaining 6 are very likely fine — but haven't been proven live the way the plan's verification step called for.

- **3.3.62 — fixed the Settings save bug found during that verification.** Root cause: `SaveBar` (`src/shared/components.js`) did `<Button onClick={ onSave } ...>`, so WordPress's `Button` passed the raw click event straight through as `onSave`'s first argument. The top-level `onSave` in `src/settings-app/index.js` treats that argument as an `overrideData` object and spreads it into the save payload (`{ ...(overrideData || data) }`) — spreading a React synthetic event pulls in circular fiber/DOM references, so `apiFetch`'s internal `JSON.stringify()` threw before any request was sent, and the tab's state silently reverted on reload. Affected every Settings tab that wired `SaveBar` directly to the shared `onSave` — Interface, Security, Memory, Agents, Instructions (Users and Endpoints already worked around it locally with a no-arg wrapper, `() => onSave()`). Fix: `SaveBar`'s button now calls `() => onSave()`, one line, fixes all five tabs at once. Verified live on lffci.org: toggled Interface mode to Advanced, saw "Settings saved.", reloaded, setting persisted; reverted back to Basic afterward. `debug.log` clean (only a pre-existing, unrelated Rank Math SEO warning).
- **3.3.63 — standardized the Basic/Advanced switch, fixed dead batch-approve, fixed table width.** Three related fixes from a browser-driven pass over Tools/Skills/Approvals/Activity, the four screens with a Basic/Advanced content split:
  - **Standardized switch placement.** The switch previously lived inline in body-copy paragraphs, worded differently per page, and Skills had no switch at all (silently inherited the global default with no way to override it per-screen). Moved into `AdminPage`'s existing `actions` slot (top-right), same spot on all four screens now. `ScreenModeToggle` is rendered once, centrally, in `AdminPagesApp` — see `SCREENS_WITH_MODE` in `src/admin-pages/index.js`.
  - **Approvals bulk approve was fully dead, not just hard to find.** Advanced mode's only distinguishing feature was an "Open classic queue" link. Two bugs stacked: the `classic=1` query param it generated was never read anywhere in `Admin_Menu_Handler::render_page()` (unlike the `tab=backups` special-case right next to where that check should have been), and even the classic page it would have reached (`admin/approvals.php`) had its batch-approve buttons (`agentic-approve-all-btn` etc.) with zero JS anywhere in the codebase wiring them up — dead on arrival, apparently orphaned when Approvals moved to React. Rather than resurrect that page, built real bulk approve/reject natively in the React view: `group_pending_for_bulk()` (`class-admin-pages-rest.php`) groups pending rows by agent + 120s window (same rule the old classic page used) and is included in `approvals_payload()` as `groups`; new `approval_decide_bulk` REST action processes a group server-side, scaffold/create actions first, stopping at the first failure for approve (reject has no such ordering need). Verified live with real inserted test rows: approve-all executed both items in DB-confirmed order, reject-all correctly skipped execution, `debug.log` clean.
  - **Table width.** All four screens (plus any future consumer of the shared `admin-pages`/`admin-list` React shell) were capped at the same `max-width: 1100px` as form-heavy pages like Settings, leaving a large empty strip on the right compared to classic `WP_List_Table` screens (e.g. Agents), which use the full content width. `AdminPage` (`src/shared/components.js`) now takes an opt-in `wide` prop (→ `.agentic-react-admin--wide { max-width: none; }`) — set by `admin-pages`/`admin-list`, left off `settings-app`/`dashboard-app` so those keep the narrower, more readable width.
  - **Operational gotcha hit while verifying this:** lffci.org sits behind Cloudflare, which edge-caches static assets (e.g. `assets/css/react-admin.css`) for 30 days keyed on the full URL including `?ver=`. A CSS-only deploy that doesn't bump `AGENT_BUILDER_VERSION` can look "not applied" in a real browser even though the file is correct on disk (hash-verified) and correct via `curl` with a cache-busting query param — Cloudflare is serving its own stale cached response for the *unchanged* `?ver=X.Y.Z` URL. No plugin-level Cloudflare integration exists on this site to purge it via WP-CLI; the practical fix is that the version bump step of the deploy workflow already solves this (new `?ver=` → cache miss) — but don't be fooled mid-session into thinking an asset-only fix didn't take when testing against an unbumped version. To force a real check before bumping, swap the stylesheet's `href` client-side (e.g. via the browser JS console) to a cache-busted URL rather than trusting a normal reload, even a hard one — the browser's own cache isn't the problem, Cloudflare's is.

Skills already got this treatment in 3.3.58; audited `Admin_Menu_Handler::register()` and found exactly two remaining menu items still gated by the site-wide default: "Publish" (`agentic-deployment`) and "Activity" (`agentic-audit-log`), both hidden from the sidebar in Basic mode via a shared `$agentic_advanced_parent` slug (`'agent-builder'` in Advanced, `''` — hidden-but-URL-reachable — in Basic). Both now always register under `'agent-builder'` unconditionally; `advanced_parent_slug()` had no other callers so it was removed rather than left dead. Verified live: set the global default to Basic, confirmed both still show in the sidebar. This also happened to leave `agentic_ui_mode` back at `basic`, its value from before any testing this session. No other menu items are gated by mode — this closes out that pattern entirely, so nothing needs the same treatment later.

### What just happened: Skills feature overhaul (3.3.57–3.3.61)

Skills (SKILL.md instruction bundles that teach agents workflows) had a complete data layer and admin UI since v2.5.2 but were **never actually wired into agent runtime** — `Skills_Registry::get_for_agent()` was dead code. This got fixed and substantially built out:

- **3.3.57** — Spec-aligned with [agentskills.io](https://agentskills.io) (the open standard Anthropic and Google's Android Skills both use): `allowed-tools` frontmatter, `license`/`compatibility`/`metadata` fields, spec validation. Wired skills into the actual prompt pipeline via progressive disclosure (name+description always in context; full body loaded on demand via a new `load_skill` tool — mirrors the existing OKF knowledge-wiki pattern). Bundled skills now auto-refresh from disk on plugin updates if never user-edited (`source_hash` tracking + a proper versioned schema migration — this surfaced and fixed a real pre-existing bug: `dbDelta()` can't parse `CREATE TABLE IF NOT EXISTS`, so this whole class of schema migration had likely been silently failing plugin-wide). Added 4 new bundled skills: `woocommerce-catalog-management`, `woocommerce-order-management`, `wp-content-authoring`, `gutenberg-blocks`.
- **3.3.58** — Skills now always shows in the admin menu (was hidden entirely in Basic mode); the Basic/Advanced split moved onto the page itself instead.
- **3.3.59** — Browse Community Skills now supports **3 sources** with a switcher: `github.com/WordPress/agent-skills` (official WordPress org repo, Basic mode default — this is the reputable, human-reviewed alternative to ClawHub's open-publish model), `github.com/anthropics/skills` (Advanced only), and OpenClaw/ClawHub (Advanced only, pre-existing). Fixed two real bugs found along the way: the import payload was `sanitize_text_field()`'d as a whole JSON blob before decoding (corrupts content with `<...>` in it — routine in WordPress examples), and cross-source dedup matched on slug alone (two registries' same-named skill could clobber each other).
- **3.3.60** — Two bugs caught by actually testing in a browser rather than trusting server-side checks: a CSS utility class's `display:flex` was silently defeating the native `hidden` attribute on the ClawHub-only search box; YAML block-scalar descriptions (`description: |-` — Anthropic's own `claude-api` skill uses this) were parsed as literally just the block indicator.
- **3.3.61** — The Basic/Advanced split from 3.3.58 only applied to the classic-PHP Skills page. The list view you actually land on from the nav renders through a **separate React component** (`SkillsView` in `src/admin-pages/index.js`, fed by `skills_payload()` in `class-admin-pages-rest.php`) that never got the same treatment. Fixed to match.

## Deploy workflow

reproduce → root-cause → fix → lint → version bump → deploy to lffci.org → verify live → check `debug.log` → commit → push. See global memory `feedback_deploy_workflow.md` for the full mechanics (scp to `/tmp`, `sudo cp` into place, `chown www-data:www-data`, hash-compare local vs remote before committing).

Live plugin path on lffci.org: `/var/www/lffci.org/public/wp-content/plugins/agent-builder` (note: directory is `agent-builder`, **not** `agent-builder-wp`). WP-CLI: `ssh lffci "sudo -u www-data wp --path=/var/www/lffci.org/public <command>"`.

**React admin surfaces** (`src/*/index.js`) need `npm run build` (wp-scripts) before deploying — the built output in `build/` is git-tracked and must be committed alongside source changes, not just the source.

## Key architecture notes

- **Basic/Advanced UI mode**: `Admin_Menu_Handler::is_advanced_mode( string $screen = '' )`, backed by the `agentic_ui_mode` option (global) with optional per-screen user-meta overrides. Established pattern for REST-fed React views: include `'is_advanced' => $is_advanced` in the payload (see `tools_payload()`/`approvals_payload()`/`logs_payload()`/`skills_payload()` in `class-admin-pages-rest.php`), consume as `data.is_advanced` in the corresponding `XxxView` component. For classic-PHP admin pages, call `is_advanced_mode('screen-name')` directly and gate markup — but remember to keep any hidden-in-Basic form field as a `<input type="hidden">` fallback so its value still round-trips on submit rather than getting silently reset.
- **Skills vs Tools vs Abilities**: Skills (`Skills_Registry`, `library/skills/*/SKILL.md`) are reusable instruction bundles teaching *how* to sequence tool calls — loaded into agent context via progressive disclosure. Tools (`Tools_Registry`, `library/tools/*/tool.php`) are the actual callable functions. Abilities (`Abilities_Manifest`, `abilities.json` per agent) are the separate *security/risk-tier* boundary — skills' `allowed-tools` is advisory scoping only, never a second permission system.
- **Mirror commits**: this repo receives periodic "mirror" commits from a separate private upstream, authored by "Agent Builder Release <support@agentic-plugin.com>", messages like "Release free (WPorg) vX.Y.Z" / "Mirror from private agent-builder". These are not something to create manually, aren't suspicious, and shouldn't be reverted/reconciled against local work — they're an established part of the workflow. Check `git log` for a newer such commit than what's live on lffci.org at the start of a session.
- **i18n**: fully built out as of 3.3.46 (11 locales, PHP `.po`/`.mo` + per-handle JS JSON). If new webpack entries or translatable strings are added, the `.pot` needs regenerating with `wp i18n make-pot . languages/agent-builder.pot --slug=agent-builder --exclude=build` (must exclude `build/` or webpack output pollutes references), and JS translations need the `make-json` output manually renamed from per-source-file to per-*handle* `{domain}-{locale}-{handle}.json` — WordPress's `load_script_textdomain()` won't find the default hashed filenames.
